## 二、知识体系 A：运动向量

### 模块 1：齐次坐标 / NDC / 透视除法

**完整管线**：

```
对象空间 --[M]--> 世界空间 --[VP]--> 裁剪空间 (x,y,z,w) --[÷w]--> NDC --[映射]--> 屏幕像素
```

**三条铁律**：

1. **w 携带深度**：`w_clip = -z_eye`。相机前方 w > 0，相机背后 w < 0，相机原点 w = 0
2. **看到 NDC 先除以 w**：裁剪空间 `(x,y,z,w)` ÷ w 才是 NDC
3. **NDC ≠ UV**：NDC 原点在屏幕中心、范围 [-1,1]；UV 原点在角、范围 [0,1]

**投影矩阵后两行**：

```
[ 0  0  A  B ]     A = -(far + near) / (far - near)     （OpenGL 约定）
[ 0  0 -1  0 ]     B = -2 * far * near / (far - near)
```

- 第四行的 `-1`：制造 w，让透视除法产生"近大远小"
- 第三行的 `A, B`：深度重映射，由"近平面 → NDC z 一端，远平面 → 另一端"两个边界条件解出

**关键认知**：想知道点多远，看 w（= -z_eye），**不看 z_clip**。

### 模块 2：URP 内置矩阵体系

**两跳**：`对象 --[M]--> 世界 --[VP]--> 裁剪`（View 和 Proj 合并成 VP）

**运动向量需要的四个矩阵**：

| 矩阵 | 含义 |
|---|---|
| `UNITY_MATRIX_M` | 当前帧，物体 → 世界 |
| `UNITY_PREV_MATRIX_M` | **上一帧**，物体 → 世界（物体自身历史） |
| `_NonJitteredViewProjMatrix` | 当前帧，世界 → 裁剪（**无抖动**） |
| `_PrevViewProjMatrix` | 上一帧，世界 → 裁剪（相机历史） |

**两条独立自由度**：`_PrevViewProjMatrix` 管**相机**的历史，`UNITY_PREV_MATRIX_M` 管**物体**的历史。缺一不可。

**`mul` 读法**：`mul(VP, mul(M, pos))` = 最靠近顶点的先作用 = `A(B(v))`。

**透视投影不可线性叠加**：正交投影下相机运动 + 物体运动的屏幕位移可拆开相加；透视投影下**不行**——因为除以 w 是非线性操作。

### 模块 3：TAA 抖动（Jitter）

**TAA 原理**：跨帧采样，每帧投影矩阵带亚像素抖动，累积后磨平边缘。

**两个副作用**：

| 需求 | 用什么位置 |
|---|---|
| 光栅化（画在哪） | **抖动**位置（否则 TAA 失效） |
| 运动向量（算位移） | **非抖动**位置（否则速度图被污染） |

**三个位置字段**：

| 字段 | 语义 | 参与位置定位？ | 用途 |
|---|---|---|---|
| `positionCS` | `SV_POSITION` | ✅ | 光栅化 |
| `positionCSNoJitter` | `POSITION_CS_NO_JITTER` | ❌ | 运动向量（当前）|
| `previousPositionCSNoJitter` | `PREV_POSITION_CS_NO_JITTER` | ❌ | 运动向量（上一帧）|

**`POSITION_CS_NO_JITTER` 的真实作用**：不参与"位置裁剪 + 像素定位"，但**仍参与顶点→插值→片元**的管线。选它而非 `TEXCOORD`，是因为需要 **float 精度**（`TEXCOORD` 常是 half，小位移会被量化吃掉）。

**jitter 量级**：亚像素级（约 0.5 像素）。慢速运动的真实位移和 jitter 同量级，抖动位置算运动向量会严重污染。

### 模块 4：CalcNdcMotionVectorFromCsPositions 内部

```
裁剪空间位置 pair
  │  ÷ w
  ▼
NDC pair
  │  相减
  ▼
NDC 位移
  │  1. y 翻转（如果 UNITY_UV_STARTS_AT_TOP）
  │  2. * 0.5
  ▼
UV space offset
```

**为什么 `* 0.5`**：NDC 长度 2，UV 长度 1，比 = 1/2。位移转换时 `+0.5` 相减抵消，只剩缩放。

**为什么 y 翻转**：NDC 的 y 向上；D3D 的 UV 原点在左上、v 向下。`UNITY_UV_STARTS_AT_TOP` 为真时必须翻转。

**为什么后处理要 UV space**：后处理采样历史帧用 UV，直接给 UV offset 最省事。

### 模块 5：ApplyMotionVectorZBias

**作用**：把物体裁剪空间 z 往相机方向推极小量，防止运动向量纹理出现缝隙。

**缝隙成因**：GPU 光栅化对三角形边缘像素归属判定的边界情况，可能出现空洞。

**为什么乘 `positionCS.w`**：让 NDC 上变化固定量 Δ，分子需加 `Δ * w`，保证所有距离的偏移量透视一致。

**和 `ApplyShadowBias` 的对比**：

| | ApplyShadowBias | ApplyMotionVectorZBias |
|---|---|---|
| 防什么 | 阴影自遮挡条纹 | 运动向量纹理缝隙 |
| 偏移方向 | 沿光源方向 | 沿相机方向 |

## 三、知识体系 B：法线贴图

### 第一层：法线是什么

- 顶点法线（数据自带，语义 `NORMAL`）
- 面法线（叉乘算）
- GPU 用**顶点法线 + 插值**，让平面看起来有弧度
- 法线是**单位向量**（`length == 1`），这个约束贯穿全话题

### 第二层：为什么要法线贴图

- 加几何 → 顶点爆炸；用法线贴图 → 逐像素改法线方向，光照出凹凸
- **不改变几何，只改变"光照认为的表面朝向"**
- 存储编码：`color = normal * 0.5 + 0.5`；平坦法线 `(0,0,1)` → `(0.5,0.5,1)` → 淡蓝色
- 法线参与**整个光照计算**（N·L、N·H、反射探针、阴影偏移），不只是"与光方向点乘"

### 第三层：三种空间

| 空间 | 相对谁 | 旋转 | 变形 | 复用 |
|---|---|---|---|---|
| 对象空间 | 模型局部轴 | ❌ | ❌ | ❌ |
| 世界空间 | 世界轴 | ❌ | ❌ | ❌ |
| **切线空间** | **表面 TBN** | ✅ | ✅ | ✅ |

**切线空间是唯一同时满足"旋转 + 变形 + 复用"的方案，工业标准。**

### 第四层：TBN 三剑客

| 向量 | 从哪来 | 说明 |
|---|---|---|
| T（Tangent） | 顶点数据 `TANGENT`（float4）| 沿表面 UV 的 u 方向 |
| B（Bitangent） | `sgn * cross(N, T)` | 副切线，**不存**，算出来 |
| N（Normal） | 顶点数据 `NORMAL` | 表面法线 |

**手性 `tangent.w`**：记录 TBN 是左手系还是右手系。镜像 UV / 负缩放会翻转手性，必须用 `sgn` 修正 B：

```hlsl
half sgn = input.tangentWS.w;
half3 bitangent = sgn * cross(input.normalWS.xyz, input.tangentWS.xyz);
```

**负缩放检测**：`GetOddNegativeScale()`（奇数个负轴 → 翻转）：
```hlsl
real sign = input.tangentOS.w * GetOddNegativeScale();
```

**TBN 矩阵**：列向量排列 `half3x3(T, B, N)`，`normalWS = TBN × normalTS`。

**合法 TBN 三条件**：
1. 三向量两两正交
2. 三向量长度都为 1
3. 手性一致

### 第五层：工程问题

**压缩**：

| 格式 | 每像素 | 适配 |
|---|---|---|
| RGB8 | 24 bit | 完美但显存大 |
| DXT / BC1 | 4 bit | ❌ 法线不友好（按块颜色插值）|
| **BC5** | 8 bit | ✅ 两通道 8bit，法线专用 |

**两通道 + z 重建**：切线空间法线 z 通常 > 0，可只存 xy，`z = sqrt(saturate(1 - x² - y²))`。**世界空间法线不能用**（z 可能为负）。

**sRGB 陷阱**：

| 贴图类型 | 导入设置 |
|---|---|
| 颜色贴图（albedo）| sRGB |
| 法线贴图 | **Linear** |
| 金属度 / 粗糙度 / AO / 高度 | Linear |

准则：**是不是"人眼看到的颜色"？是 → sRGB，否 → Linear。** 法线是方向数据，sRGB 转换会扭曲 xyz → 光照全错。

**Green channel（GL / DX）**：
- OpenGL：y 向上为正（Unity 用这个）
- DirectX：y 向下为正（翻转）
- 文件名后缀：`_GL` / `_DX`
- 出错表现：**整个模型凹凸像凹的** → 翻转 y 分量

**Mipmap**：多像素平均会抵消相反法线 → 平坦化。**采样后必须归一化**（否则长度 < 1，光照变暗）。

### 第六层：变形 / 蒙皮 / 镜像 UV

- 骨骼变形时，N、T 都要跟着更新（用骨骼矩阵）
- **镜像 UV**：u 方向反 → 手性翻转 → `tangent.w` 修正
- **负缩放**：`GetOddNegativeScale()` 检测
- **顶点动画 / GPU Skinning**：对象空间 N/T/B 被改写，但光照**仍然用世界空间 TBN**

## 四、错题本

### A 组：除以 w（早期反复错）

| 题 | 错因 | 纠正 |
|---|---|---|
| 算 NDC 时直接用 z_clip | **忘了除以 w** | 看到 NDC，先 ÷ w，无例外 |
| w = 0 对应什么位置 | 答"深度为 0 的平面" | **相机原点**（w_clip = -z_e = 0 → z_e = 0）|
| 判断点前后 | 看 z_clip 符号 | **看 w 符号**：w > 0 前方，w < 0 后方 |

**核心**：`w_clip = -z_eye` 是"点是否可见"的开关，不只是"要除的那个数"。

### B 组：矩阵与线性（模块 2）

| 题 | 错因 | 纠正 |
|---|---|---|
| "相机 + 物体位移可叠加" | 答"非线性不能拆"方向对，但理由没说清 | **透视除法是非线性的**，这是根本原因 |
| 旋转角度 30° → 32° | 答"转过 62°" | **转过 2°**。绝对角度 vs 增量的混淆 |
| "能用矩阵的都是线性操作" | 这个说法错 | **平移（仿射）、投影（非线性）都不是线性变换** |

**核心**：矩阵是工具，不是保证。是否线性取决于变换内容。

### C 组：TAA 抖动（模块 3）

| 题 | 错因 | 纠正 |
|---|---|---|
| `POSITION_CS_NO_JITTER` 作用 | 答"不经过光栅化" | 它**不参与位置定位，但仍参与插值** |
| jitter 引入环节 | 答"光栅化引入 jitter" | jitter 在**顶点阶段就已加入**（VP 矩阵含抖动）|

### D 组：TBN 与空间（法线部分，后期反复错）

| 题 | 错因 | 纠正 |
|---|---|---|
| 相机环绕，TBN 变吗 | 答"会变" | **TBN 只跟物体几何有关，与相机无关** |
| 世界空间 TBN 跟相机有关吗 | 漏选 B、E | **世界空间 TBN 也只跟物体有关**（`UNITY_MATRIX_M` 不含相机）|
| 物体绕 Y 轴转 90°，世界空间 TBN 变吗 | 答"不变" | **变**！世界空间 TBN 跟着物体转 |
| 顶点动画用哪个 TBN | 答"对象空间" | **光照永远用世界空间 TBN** |

**核心**：
> **TBN 只跟物体有关，跟相机无关。相机只影响 viewDir。**
> **光照计算永远用世界空间 TBN，不管数据来自哪里。**

### E 组：叉乘计算（中间错几次）

| 题 | 错因 | 纠正 |
|---|---|---|
| `cross((0,0,1), (0,1,0))` | 答 `(1,0,0)` | **`(-1,0,0)`**。第二、三项符号易错 |

**叉乘 3 步法**：
1. 写公式 `(Ay*Bz - Az*By, Az*Bx - Ax*Bz, Ax*By - Ay*Bx)`
2. 逐步代入，不要跳步
3. **验算**：两向量所在平面 → 结果垂直于该平面；正交向量 → |cross| = |a|*|b|

**反交换律**：`A × B = -(B × A)`

### F 组：法线工程问题

| 题 | 错因 | 纠正 |
|---|---|---|
| 镜像 UV 出问题要翻转什么 | 答"翻转法线" | **修正副切线方向**（`B = sgn * cross(N, T)`），法线 N 不受手性影响 |
| "凹凸像凹的" 原因 | 答"副切线手性" | **全模型反 = green channel（GL/DX）**；**半边反 = 手性** |
| TBN 非法，原因 | 答"副切线算错" | 输入数据问题（切线生成失败 / UV 退化）|

### G 组：变体计算与优化（Part5 第八节）

| 题 | 错因 | 纠正 |
|---|---|---|
| `multi_compile _ _A _B _C` 几份 | 答 3 | **4 份**。开头的 `_` 是默认变体，也是 token |
| `multi_compile _ _MAIN_LIGHT_SHADOWS _MAIN_LIGHT_SHADOWS_CASCADE` | 答 2 | **3 份**（默认 + 两个关键字）|
| Variant Stripping 能剥哪些 | 答"material 级" | **只对 `multi_compile` 有意义**，`shader_feature` 本身已按需编译 |
| 优化维度 | 只想到"改 pragma" | **两层都要看**：Shader 层（pragma 写法）+ 构建层（Variant Stripping）|
| 抽象 vs 具体动作 | 答"让 URP 剥离变体" | 这是"目标状态"不是"动作"。应写"移除那行 Cookie pragma" |

**核心结论**：

> **`shader_feature` = 只编用到的（已省）；`multi_compile` = 全编（需要 Strip）**
> **Variant Stripping 是给 `multi_compile` 用的，不是给 `shader_feature` 用的。**
